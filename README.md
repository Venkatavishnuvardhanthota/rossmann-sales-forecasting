# Rossmann Store Sales Forecasting Pipeline

## Business Problem

Rossmann operates 1,115 drugstores across Germany. Accurate daily sales
forecasting can support staffing, inventory planning, and promotional
decisions. This project builds an end-to-end analytics and forecasting
pipeline covering SQL data preparation, exploratory analysis, forecasting
with Prophet and XGBoost, model evaluation, and Power BI reporting.

The forecasting work evaluates store-day sales using a chronological
84-day holdout period, and separately aggregates XGBoost's predictions
to chain-wide daily totals for comparison against Prophet.

## Why This Project Goes Beyond a Beginner Pipeline

- Two forecasting approaches (Prophet and XGBoost) built, tuned, and
  honestly compared — not just one model presented as "the answer"
- A documented, evidence-based tuning arc for each model, with the
  reasoning behind each change stated, not just the final number
- An ensemble blend was tested and found *not* to improve on the best
  individual model — a negative result reported honestly, not omitted
- A star-schema Power BI dashboard (`Dim_Date` connected to three fact
  tables) with 10 DAX measures, not flat CSV charts
- Multiple real data-quality bugs found and fixed across the pipeline
  (see **Data Quality Notes**) — the debugging process is part of the
  deliverable, not hidden

## How to Run

1. Download `train.csv` and `store.csv` from Kaggle and place them in
   `data/raw/`.

2. Set up MySQL and run:

   ```sql
   sql/01_create_tables.sql
   sql/02_load_data.sql
   ```

   The loading script contains a hardcoded local file path and uses
   `LOAD DATA LOCAL INFILE`. Edit the paths to match your machine and
   confirm that `local_infile` is enabled on your MySQL server:

   ```sql
   SHOW VARIABLES LIKE 'local_infile';
   ```

3. Run:

   ```text
   sql/query7_export_full_merged_dataset.sql
   ```

   Its output, `train_store_merged.csv`, is the dataset used by the
   Python phase.

   Queries 1–6 are independent business-question analyses. They are not
   sequential pipeline steps and can be run in any order.

4. Create a virtual environment and install the dependencies:

   ```bash
   pip install -r requirements.txt
   ```

5. Run:

   ```text
   notebooks/01_eda_and_cleaning.ipynb
   ```

   Run the notebook end to end.

6. Run:

   ```text
   notebooks/02_forecasting_models.ipynb
   ```

   Run the notebook end to end. This generates and saves the trained
   model artifacts to `model/`.

7. Open:

   ```text
   dashboard/RossmannSalesDashboard.pbix
   ```

   in Power BI Desktop.

## Key Findings

1. **December sales spike ~17–18% month-over-month**, then correct by a
   similar magnitude in January — observed consistently across the
   preliminary Excel analysis, SQL analysis, and Python analysis.

2. **StoreType B consistently outperforms** and is structurally distinct:
   it is the rarest store type, the only format carrying Assortment B,
   and the most consistently open.

3. **Every analyzed store showed a positive average-sales lift on
   promotional days**, though the size of that lift varied widely
   (19–82% per store; 38.77% chain-wide).

4. **Saturday, not Sunday, is the lowest-selling day** of the week, even
   among stores that remain open.

5. **Stores with very large competition distances did not reach the
   highest observed sales levels, while stores closer to competitors
   showed a wide range of performance.** This suggests that competition
   distance alone does not explain sales; store format and local demand
   may also play a role.

6. **March and July also show recurring seasonal upticks** (~16–17%
   month-over-month), independent of calendar day-count differences.

## Modeling & Validation Methodology

Models were compared on a single chronological 84-day held-out
validation period (the last 12 weeks of available data), rather than a
random split, which could leak future information into training.

This is a lighter-weight evaluation than rolling-origin backtesting
across multiple windows. Results should therefore be interpreted as
evidence from one representative validation period, not as a universal
guarantee of forecast accuracy.

### Prophet

The final Prophet benchmark was the holiday-aware model, which achieved
**32.89% MAPE**.

Prophet was evaluated using the actual validation-period `Promo` values
as a known regressor. This means the validation forecast is conditional
on a known promotion schedule rather than being a fully blind forecast.

A tuned Prophet variant achieved a lower MAPE of **22.48%**, but it was not
selected because its MAE and RMSE were higher than those of the
holiday-aware model.

### XGBoost

XGBoost was tuned using `RandomizedSearchCV` with chronologically ordered
folds via `TimeSeriesSplit`.

Rows were sorted by date before splitting. Because many stores share the
same calendar date, however, a fold boundary can fall within a single
date rather than strictly between dates. The procedure is therefore
chronologically ordered at the row level, not a fully date-grouped
time-series split.

The final XGBoost model achieved:

- **17.13% MAPE** at the store-day level
- **≈ 1,062 MAE** sales units per store-day
- **≈ 1,493 RMSE** sales units per store-day
- **8.20% MAPE** when predictions were aggregated to chain-wide daily
  totals

These are two evaluation grains for the same model, not two different
models. The store-day metric is the more directly relevant measure for
individual-store staffing and inventory decisions.

### Production Forecast

The production forecast model differs from the validated model.

It is retrained on all historical data with `Promo` excluded because
future promotion schedules are not genuinely known ahead of time.

Therefore, the **17.13% validation MAPE** describes the accuracy of the
validated model under its evaluation conditions. It should not be
interpreted as a guaranteed error rate for the actual 12-week forward
forecast, which has less information available.

### Ensemble

An ensemble blend of Prophet and XGBoost was tested and did not improve
on XGBoost alone. This negative result is reported rather than omitted.

## Data Quality Notes

- `CompetitionDistance` missing values were imputed with the column
  median (chosen over the mean for greater resistance to outliers).
  These values are estimates, not measured distances.

- `rossmann_cleaned.csv` excludes closed-store and zero-sale days because
  these represent non-operation rather than observed positive demand.
  It should therefore not be used to analyze closure frequency or
  holiday shutdown patterns.

- The full, unfiltered dataset, `train_store_merged.csv`, is retained
  separately for analyses that require all store-day records.

- Several real data-quality bugs were found and fixed during the build:
  - a MySQL date-format mismatch causing non-chronological month sorting
  - fabricated zero values caused by an unhandled `NULL` import
  - a mislabeled low-sales weekday finding corrected from Sunday to
    Saturday

## Limitations & Future Improvements

- Single 84-day validation window rather than rolling-origin backtesting
- No confidence intervals on the production XGBoost forecast
- Prophet retains confidence-interval capability, but was less accurate
  than XGBoost in the evaluated validation period
- Store-level rolling and lag sales features were not included and may
  improve forecasting accuracy further
- `TimeSeriesSplit` during hyperparameter search is chronological at the
  row level rather than strictly grouped by calendar date
